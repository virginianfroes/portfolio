Entrevista com SME: Guia de perguntas

Este documento reúne um roteiro de perguntas para conduzir entrevistas com Subject Matter Experts (SMEs) antes de iniciar a produção de uma documentação. O objetivo é extrair, de forma estruturada, as informações necessárias sobre o produto, feature ou atualização para que o usuário final consiga concluir sua tarefa com sucesso ao consultar a documentação.

Para o tech writer, esse guia cumpre duas funções principais: agiliza a condução da entrevista, ao garantir que nenhum ponto essencial seja esquecido, e ajuda o SME a se preparar com antecedência, já que o roteiro pode ser compartilhado antes da reunião.

Quando usar este guia

Use este roteiro antes de documentar uma feature nova, uma atualização relevante ou um fluxo pouco documentado, sempre que houver um SME disponível para entrevista.

Nem todos os blocos se aplicam a todas as situações: para uma atualização pequena, por exemplo, o Bloco 1 (Contextualização) pode ser resumido, enquanto o Bloco 3 (Resultados e erros) tende a ganhar mais peso. Adapte a ordem e a profundidade das perguntas ao escopo do que está sendo documentado.

Antes de começar

  • Pesquise e estude sobre o tema antes da entrevista.
  • Contextualize o SME e envie este guia para que ele possa se preparar previamente.
  • Peça permissão ao SME para gravar e transcrever a entrevista. Isso será útil para consultar o material posteriormente.
  • Confirme se existem informações confidenciais que não devem ser exibidas na documentação.

Guia de perguntas

Bloco 1 — Contextualização

  • Como essa feature/atualização funciona?
    • Qual é o principal objetivo que o usuário quer atingir?
  • Quem é o principal público-alvo dessa feature?
    • Qual o perfil do usuário que vai utilizar essa feature? Para quem ela foi pensada?
    • Que tipo de indústria se beneficia dela?
  • Quando essa feature será lançada?
    • Ela estará disponível para todos os usuários?
    • Onde ela estará disponível?
  • Existem pré-requisitos para o uso dessa feature?
    • Que conhecimentos pré-existentes podemos presumir que o usuário já possui?
  • Você pode demonstrar como é o fluxo típico dessa feature?

Bloco 2 — Impacto para o usuário

  • Qual o impacto direto para o usuário?
    • Que problemas ele vai conseguir resolver?
  • O que muda em relação ao que foi lançado anteriormente?
    • Existem mudanças de UI?
    • Existem mudanças no fluxo de trabalho?
  • Quais são as permissões necessárias para cada etapa do fluxo de trabalho?
    • É necessário que o usuário tenha novas permissões para executar alguma tarefa?
  • É necessário que o usuário execute alguma ação para que essa feature seja ativada?

Bloco 3 — Resultados e erros

  • Qual é o resultado esperado do uso dessa feature?
    • Qual é o resultado de um fluxo bem-sucedido?
  • Quais são os problemas potenciais que podem surgir com essa feature?
    • Quais são os erros e riscos mais comuns?
    • Como resolvê-los?
  • Você pode dar exemplos de resultados do uso da feature?
    • Quais são os casos de uso mais comuns?
  • Em que momento geralmente surge confusão no processo?
    • Quais são as dúvidas mais frequentes em relação a essa feature?

Bloco 4 — Encerramento

  • O que é absolutamente indispensável incluir e o que podemos deixar de fora sem problemas?
  • Existem boas práticas que devem ser incluídas?
  • Existem documentos ou recursos complementares que possam ser analisados?
    • Por exemplo, PRDs, protótipos ou código.

Após a entrevista

  • Pergunte ao SME se você pode contatá-lo para futuras atualizações ou revisões técnicas. Caso ele não esteja disponível, pergunte quem é a melhor pessoa para procurar.
  • Reduza o retrabalho validando a documentação com o SME antes da publicação.

Por que usar este guia

Um roteiro estruturado de entrevista reduz o número de follow-ups necessários após a conversa, diminui o risco de lacunas de informação na documentação final e torna o processo mais previsível tanto para o tech writer quanto para o SME.

Na prática, isso significa menos idas e vindas por e-mail ou Slack, menos retrabalho na revisão técnica e um ciclo de documentação mais curto do briefing à publicação.
